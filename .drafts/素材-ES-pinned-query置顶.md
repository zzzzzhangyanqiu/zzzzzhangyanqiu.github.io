# ES pinned query：原生「搜索置顶」

> 博客素材卡。约定：报这个标题即指代本卡内容。
> 事实已核对官方文档 + 官方论坛（2026-06 核），标注了确信度。

**主旨**：`pinned` query 是 Elasticsearch 原生的「置顶」——把指定的几篇文档强行顶到结果最前面，排在所有「自然结果」之上，顺序按给定顺序来，不受相关性打分影响。对应业务里的「编辑加权 / 运营置顶 / 赞助位」。

---

## 结构（已核对官方文档）

- **`organic`（必填）**：剩下的「自然结果」用的查询，排在被置顶文档下面，按正常相关性排序。
- **置顶文档两种写法，二选一**：
  - **`ids`**：一组文档 `_id`，按给定顺序出现。
  - **`docs`**：按顺序的数组，每项 `_id` + 可选 `_index`，能**跨索引/指定索引**精确定位（比 `ids` 新、更灵活）。

```json
GET /products/_search
{
  "query": {
    "pinned": {
      "ids": ["sku-1", "sku-4", "sku-100"],
      "organic": { "match": { "title": "iphone" } }
    }
  }
}
```

```json
// docs 写法：可跨索引
"pinned": {
  "docs": [
    { "_index": "products", "_id": "sku-1" },
    { "_id": "sku-4" }
  ],
  "organic": { "match": { "title": "iphone" } }
}
```

## 容易踩的点 / 边界（已核对）

1. **只对「按相关性排序」生效**：查询里一旦写了显式 `sort`，置顶就被盖掉了（官方原文：pinned 设计上只配合 relevance-based sorting）。
2. **置顶上限 100 篇，且不可配置**（官方论坛确认）：超过只取前 100。
3. **实现原理**：被置顶的文档被赋予高于自然结果的分值来保证排在最前，并按给定顺序排列。

## 进阶（写博客时可延伸，细节待核实）

`pinned` query 是「手动指定 id 置顶」。更进阶的是 **Query Rules（查询规则）**：按条件（如某个搜索词、某些 metadata）规则化地触发置顶/排除，相当于把「置顶」从硬编码 id 升级成可配置规则。Query Rules 的具体能力与**许可层级待核实**，别凭印象写。

## 和用户业务的关联（写作切入点）

用户线上有「搜索置顶」需求（`search-rerank` 技能 / `search_rerank_config` 配置表），目前是**应用层**改排序。pinned query 是**ES 原生**在查询里直接置顶。两条路的取舍，正是好博客题材：

- **应用层 rerank**（现状）：置顶逻辑在自己服务里，灵活、好审计、可跨数据源、改规则不动 ES；代价是要自己维护一层、和 ES 的分页/排序耦合时容易出 bug。
- **ES 原生 pinned**：省一层、跟着 ES 的排序与分页天然走；代价是置顶名单要进查询、受 100 上限约束、跨业务规则不如应用层自由。

潜在标题方向：《置顶这件事，放应用层还是放 ES？》——延续「机制 + 取舍」的一贯调性。

关联：与 ES 系列（[[一份数据怎么被切碎又拼回来]] 等）同属 Elasticsearch 主题；置顶本质是「人工干预相关性排序」，可呼应《三选二》里「精准/相关性」那条线。
