# ES _search 的 preference（控制请求落到哪个分片副本）

> 博客素材卡。约定：报这个标题即指代本卡内容。
> 状态：**先简单存着**，未深考证，真要成文时再逐条核实当下版本的官方说法（[[blog-accuracy-first]]）。

**一句话**：`_search` 的 `preference` 参数，用来控制这次查询请求被路由到分片的**哪一份副本**（primary / 某个 replica）上执行。

---

## 默认行为

- 一个 shard 通常有多份副本（primary + replicas），数据等价。
- 不指定 preference 时，ES 用 **自适应副本选择（Adaptive Replica Selection, ARS）** 在副本间挑一个"当前最快"的来执行，每次不一定是同一份。

## preference 能干嘛

- 给一个**自定义字符串**（比如用 userId、sessionId），ES 保证：只要分片集合不变，相同字符串的请求会**固定落到同一批副本**上。
- 也有内置值：`_local`（优先本地分片）、`_only_local`、`_shards:0,1`（指定分片）等；`_primary` / `_replica` 这类旧值在新版本已弃用——**成文时必须核实**。

## 为什么需要它（核心张力，值得写）

- 不同副本的 **refresh 时机、段合并状态**可能略有差异 → 同一个查询在不同副本上，**打分/排序可能略不同**。
- 后果：用户翻页或刷新时，本来同一批结果**顺序发生抖动**（俗称 "bouncing results"）。
- 用 `preference=<固定字符串>` 把同一用户的连续请求钉在同一副本上 → 结果稳定、翻页一致。

## 代价 / 权衡

- 固定副本会**牺牲负载均衡**：所有请求挤到同一副本，热点副本压力大，ARS 的"挑最快"优势也没了。
- 所以是"一致性 vs 负载均衡"的取舍，按场景用。
