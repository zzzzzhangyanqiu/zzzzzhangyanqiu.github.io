# ES 查询性能优化实战（filesystem cache / 预热 / 冷热分离 / 分页）

> 博客素材卡。约定：报这个标题即指代本卡内容。
> 来源：用户旧笔记《搜索引擎.md》里「几十亿数据量级优化性能」一段，从写入主线文章里拆出来另存，气质偏**运维调优实战**，与「机制+视角」的文章不是一路，将来单独成实战篇。

**主旨**：ES 查询快不快，很大程度取决于热数据能不能待在内存（`filesystem cache`）里。下面几招都是围绕「让该热的数据留在内存、别被冷数据冲掉」。

---

## 1. 杀手锏：filesystem cache

- ES 数据存磁盘，但查询会把数据缓存进 `filesystem cache`（OS 文件缓存，在内存里），下次直接走缓存，极快。
- ES 搜索严重依赖它：内存若能装下大部分 `segment` 索引文件，搜索基本走内存，性能极高。
- 经验阈值：留给 `filesystem cache` 的内存，**最好是数据量的 50% 以上**。
- 例：1T 数据、3 台 64G 机器，JVM Heap 各 32G、cache 各 32G → 总 cache 96G ≈ 数据量的 1/10，九成查询还得落盘，必然慢。

## 2. 只存该搜的字段（给 cache 减负）

- 只把检索/展示要用的关键字段放进 ES（如 `id`、`name`），其余大字段（`text` 正文等）放 MySQL / Mongo。
- ES 数据量小了，`filesystem cache` 就能装下更高比例，命中率上去了。
- 代价/权衡：查详情要回源到另一个库，多一跳。

## 3. 数据预热

- 后台定时任务，主动访问热点数据，把它提前刷进 `filesystem cache`，真用户来了直接走内存。
- 例：微博大 V、电商爆款（iphone）这类高频数据，每隔一会儿自动查一遍喂缓存。

## 4. 冷热分离

- 类比 MySQL 水平拆分：冷数据（访问少）写一个索引，热数据（访问频繁）写另一个索引。
- 目的：让热数据预热后**稳稳留在 cache 里**，别被冷数据的查询把它冲刷掉。

## 5. 分页（深翻页）别用 from+size

- ES 深翻页坑：查第 100 页（每页 10），每个 `shard` 要把前 1000 条都交给协调节点，5 个 shard 就是 5000 条，协调节点合并排序后只取最后 10 条。翻得越深越慢。
- 旧笔记给的解法是 `scroll`，但 **scroll 已不推荐用于交互翻页**（它是为导出/快照设计的，且官方更推 `search_after` + PIT）。
- **更新建议**：交互式深翻页用 `search_after`（配 Point In Time）；`scroll` 仅用于一次性全量导出。产品侧也可把「跳页」改成「滚动加载」，回避深翻页。
