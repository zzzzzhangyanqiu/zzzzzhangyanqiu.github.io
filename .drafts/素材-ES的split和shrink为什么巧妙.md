# ES 的 _split / _shrink 为什么巧妙

> 博客素材卡。约定：报这个标题即指代本卡内容。

**主旨**：ES 主分片数建好就锁死（见 [[素材-一份数据怎么被切碎又拼回来]]），但 `_split`/`_shrink` 居然能改分片数。它不是「热加分片」，而是靠**三个巧劲**把「重新分布数据」这件本该很贵的事做得很便宜：① Lucene segment 不可变 → ② 硬链接复用文件、不复制字节 → ③ 建索引时预留「虚拟路由空间」，让拆分可计算。**值得学的点不是 API，是这三招怎么把一个「贵操作」拆成「便宜操作」。**

---

## 一、一个前提事实（整张卡的地基）

**Lucene 的 segment 文件是不可变的（immutable）**：一旦写到磁盘就再也不改，新数据只会写进新 segment。
→ 推论：既然文件永远不变，**多个索引目录可以安全地共享同一份物理文件**，不用怕谁改了影响谁。这是下面所有「便宜」的根。

## 二、`_shrink`（减分片，如 5 → 1）：本质是「合并目录指针」

- 要做的事：把 5 个源分片塞进 1 个目标分片。
- 巧在哪：**不复制数据**，而是用**硬链接（hard link）**——目标分片目录里的文件，直接指向 5 个源 segment 在磁盘上的**同一份字节**。
- 因为 segment 不可变，多目录共享同一份数据完全安全。所以 shrink 很快：**它搬的是「目录里的指针」，不是几百 GB 的数据本身。**
- 约束：目标分片数要能**整除**源数（5→1、5→5 不行只能 5→1；6→3、6→2 都行）；过程索引只读。

## 三、`_split`（加分片，如 1 → 5）：靠「预留的虚拟空间」让拆分可计算

这才是最容易卡住的地方。**直觉的疑问**：加分片不是会让 routing 取模的分母变、把老文档全打乱吗？

ES 提前埋了伏笔：

1. 建索引时有个 `number_of_routing_shards`，文档**不是直接 hash 到实际分片**，而是先 hash 到一个**更大的「虚拟分片空间」**，再由虚拟空间映射到实际分片。
2. 这个虚拟空间是**预留好、固定不变**的。所以做 split 时，一个源分片里的文档该去哪几个新分片，是**按预留映射确定性算出来的**，不需要把全表重新 hash 到任意位置。

具体动作：

- 同样用**硬链接**把源 segment 链到 N 个新分片目录（还是不复制字节）；
- 然后每个新分片把「按虚拟空间映射、不属于自己」的文档用 Lucene 的**删除标记逻辑删掉**（不是物理搬走）。
- 净效果：一份数据被「逻辑上」切成了 N 份，物理上还是共享 + 打删除标记，背景 merge 时才真正清理。

> 关键直觉：**ES 不是 split 时才想办法拆，而是建索引那一刻就预留了「将来能整齐拆开」的结构。** 拆分变成查表，而不是重算。

## 四、所以「为什么不算热扩容」——三条硬限制

1. **过程中索引必须只读**（block writes）→ 不是在线弹性。
2. **只能按约数 / 倍数变**（shrink 要整除；split 受 `number_of_routing_shards` 上限约束）→ 不能 5→7 这种任意数。
3. **底层仍是重组一份数据**（hard link + 逻辑删 / 合并）→ 只是靠「不可变 + 硬链接 + 预留空间」省掉了复制字节，比手动 `reindex` 省事而已。

对比一致性哈希系统「加节点、在线自动 rebalance、照常读写」（见 [[素材-一致性哈希-加节点只迁一小部分]]）——ES 的 split/shrink 是**离线、受约束、一次性**的重组，是另一种性质。

## 底层原理（题眼，也是最值得学的设计思想）

> **把「贵操作」变「便宜操作」的三连招：让数据不可变（于是能共享）→ 用指针/硬链接共享（于是不复制）→ 把变化提前预留进结构（于是拆分可计算而非重算）。**
> 这套思路不止 ES 用——CoW 文件系统、Git 的对象存储、不可变数据结构，骨子里都是「不可变 + 共享 + 结构预留」。

## 一句话记忆点

> 不可变让你敢共享，硬链接让共享不花钱，预留路由空间让「拆」变成查表——三招合起来，把全量迁移降成了改指针。

## 深挖待办（正式写这篇时再补，别忘）

用户对第三章「预留虚拟路由空间」这招还没完全吃透。真写时用下面任一方式把它讲透：

- **手绘风小图**：画「文档 → 虚拟分片空间（固定不变）→ 实际分片」三层。左边 split 前实际只有 1 个分片，右边 split 后实际变成 2 个，但**中间那层虚拟空间不变**——直观看到「实际分片只是虚拟空间的不同切法，所以拆分不用重算 hash」。
- **数字手算例子**：取 `number_of_routing_shards=4`、实际主分片从 1 → 2。手算几个文档：`routing_shard = hash(_id) % 4`（这一层永远不变）；实际分片 = `routing_shard` 按区间映射（1 分片时 0~3 全归 shard0；2 分片时 0~1 归 shard0、2~3 归 shard1）。让读者看到**同一个文档在 split 前后，hash 值没变、只是落点区间被重新切了一刀**，归属是确定性对上的、零重算。

> 这两招二选一即可，目的都是让读者亲眼看到「拆分 = 查表/切区间，不是 re-hash」。
