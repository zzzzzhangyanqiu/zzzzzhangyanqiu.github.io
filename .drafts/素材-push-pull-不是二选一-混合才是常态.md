# push/pull 不是二选一，混合才是常态

> 博客素材卡。约定：报这个标题即指代本卡内容。

**主旨**：纯 push 或纯 pull 的系统很少。混用之所以普遍，是因为它能**同时拿到两端的知识**——上游的「新鲜度知识」（有没有新数据）+ 下游的「能力知识」（吃不吃得下）。

## 两种典型混合模式

1. **挂起的 pull（长轮询 / 流式拉取）**
   - 下游发起请求 → 保住背压 + 穿得过 NAT；但请求**挂起不立刻返回**，等上游有数据才回 → 又拿到 push 的低延迟。
   - 本质：用一次 pull 的「壳」，换 push 的「实时」。消掉了普通轮询的空跑。
   - 例：Kafka consumer 的 long-poll fetch、SSE、gRPC streaming、HTTP long-polling。

2. **push 通知 + pull 取数（notify-then-pull）**
   - 上游 push 一个**很小的信号**「有新东西了」 → 下游收到后自己再 pull 真正的数据。
   - **通知走 push 抢延迟，搬运走 pull 保背压。**
   - 例：Webhook（「来取吧」）、数据库 CDC、移动推送（APNs/FCM 推个唤醒、App 再拉详情）、IMAP IDLE。

## 底层原理（这段的「题眼」）

把数据流拆成**「信号」和「传输」两个动作**，分别选模式：信号轻、要快 → push；传输重、要稳 → pull。两端知识各取所需。

## 一句话记忆点

> 混合的本质，是把「什么时候有」（上游知道）和「什么时候能要」（下游知道）解耦，各用各的通道。
