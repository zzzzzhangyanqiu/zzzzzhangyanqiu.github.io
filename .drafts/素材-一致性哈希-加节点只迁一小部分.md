# 一致性哈希：加节点为什么只迁一小部分

> 博客素材卡。约定：报这个标题即指代本卡内容。

**主旨**：普通取模哈希一旦改节点数就「牵一发动全身」（几乎全量数据迁移）；一致性哈希用「环 + 顺时针归属」把迁移**局部化**——加节点平均只动 `1/N` 的数据。代价是分布不均，得靠虚拟节点补回来。这是和 [[素材-一份数据怎么被切碎又拼回来]]里 ES「取模 + 禁止扩容」相对的另一条路。

---

## 一、先看取模的软肋

- 路由公式 `hash(key) % N`，`N` 是节点数。
- `N` 从 4 变 5，**分母一换，几乎每个 key 的取模结果都变** → 几乎所有数据都要搬迁。
- 优点是均匀 + 极简，缺点是**刚性**：扩容 = 全量重映射。

## 二、一致性哈希怎么把迁移「局部化」

把节点和数据放到同一个**环**（0 ~ 2³²，首尾相接）上：

1. 节点 hash 到环上（如 A=100、B=8000、C=20000）。
2. 数据 key 也 hash 到环上，规则：**从 key 位置顺时针走，撞到的第一个节点就是它的家。**

**加节点时的关键**：在位置 5000 插入新节点 D——

- 只有「原本落在 100~5000、本来要顺时针跑去 B(8000)」的那批 key 改投 D；
- **其它区段一个都不动。**
- 平均只迁移 `1/N`，而不是全部。删节点同理：只有它名下的 key 转交给顺时针的下一个节点。

> 这就是「弹性扩容」的来源：**改变只波及环上相邻的一段弧，不波及全局。**

## 三、代价：不均匀，以及补救带来的复杂度

- **不均匀**：节点是随机落点，可能 A、B 挨得近而离 C 很远 → C 名下的弧段特别长、扛的数据特别多。节点越少越严重。
- **补救 = 虚拟节点**：一个物理节点在环上撒几十上百个「分身」，把弧段打碎、平均化。但随之要维护「虚拟点 ↔ 物理机」映射、处理上下线时一堆分身的迁移——比 `% N` 复杂得多。

## 底层原理（题眼）

> **取模是「全局函数」，改一个参数全局重算；一致性哈希是「局部邻接」，改动只波及环上相邻的一段。**
> 把「定位」从全局计算改成局部邻接关系，是它能弹性扩容的根本。

## 一句话记忆点

> 取模换均匀和简单、放弃弹性；一致性哈希换弹性、自己再想办法补均匀。没有免费的扩容。
