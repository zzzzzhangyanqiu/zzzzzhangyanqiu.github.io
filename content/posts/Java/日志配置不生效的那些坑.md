前段时间想把手头项目里某块第三方 SDK 的 INFO 日志「收一收」，别老刷屏。结果改 Nacos、改 logback、改文件名、上代码设置……折腾一圈才发现，有一半是配置被挡在了「门外」，另一半则是搞混了「日志级别」和「输出阈值」两件事。这篇就按**总 - 分 - 总**把这次踩的坑和对应知识点捋一遍，尽量说人话，方便以后自己回看，也供遇到类似问题的同学参考。

---

## 一、先说结论（总）

- **配置层面**：想通过 Nacos / logback 的「logger 级别」控制输出时，要小心三件事——Nacos 里 `logging.level.*` 可能不刷新、依赖包里的 logback 可能覆盖你的配置、控制台 appender 上的 **ThresholdFilter** 会再拦一道，把 DEBUG 挡掉。  
  实在不行，可以用 **Spring Boot 的 LoggingSystem 在启动后用代码设一次级别**，不依赖具体是 logback 还是 log4j2，一般都能生效。

- **概念层面**：代码里写的是 `log.info(...)`，这条日志的「级别」就固定是 INFO 了，**没法通过配置把它改成「按 DEBUG 输出」**。配置能做的只有一件事：给某个 logger 设一个**输出阈值**（比如 WARN），只输出「级别 ≥ 该阈值」的日志，相当于控制「输出范围」，而不是改变某一行日志的级别。

下面分两块说：先讲配置为啥不生效（坑），再讲「级别 vs 阈值」这个核心概念。

---

## 二、配置为啥不生效：几个常见坑（分）

### 1. Nacos 里配了 `logging.level.*`，重启/刷新后仍不生效

**现象**：在 Nacos 的 yaml 里写了类似：

```yaml
logging:
  level:
    com.xxx.SomeClass: DEBUG
```

发现改完重启也不起作用，或者只有部分环境生效。

**可能原因**：

- Spring Boot 的 LoggingSystem 大多在**应用启动时**读一次 `logging.*`，之后 Nacos 再改、再 refresh，一般**不会**自动把运行中的日志级别重刷一遍，所以改 Nacos 后常常要**重启**才生效。
- YAML 在 Nacos 里缩进、格式容易写错，整段 `logging` 没被正确解析，相当于没配。
- 若项目里还有**本地**的 `application.properties` / `application.yml` 或**启动参数**里带了 `--logging.level.root=INFO` 等，会覆盖 Nacos 里同名的配置。

**建议**：  
先在本地 `application.properties` 里加一行试一下，例如：  
`logging.level.com.xxx.SomeClass=DEBUG`  
能生效再考虑迁回 Nacos，并注意缩进和是否被其它配置覆盖。

---

### 2. logback 里 logger 已经设为 DEBUG，控制台仍然看不到 DEBUG

**现象**：在 `logback-level-config.xml` 里给某个包/类设了 `<logger name="com.xxx" level="DEBUG"/>`，但该类的 DEBUG 日志在控制台就是不出。

**常见原因**：控制台用的那个 **appender** 上挂了一个 **ThresholdFilter**，且阈值是 `INFO` 或 `root` 的级别。  
逻辑是：日志先按 logger 的级别过了第一关（DEBUG 允许通过），到了 appender 再被 Filter 拦一次——**低于** Filter 阈值的直接丢掉。于是 DEBUG 就在 appender 这一层被过滤掉了。

可以打个比方：  
logger 的 level 是「门卫」：只拦级别不够的（比如 logger=INFO 时，DEBUG 就进不来）。  
appender 上的 ThresholdFilter 是「二道门」：即使进了第一道门，级别低于二道门阈值的照样不让出。  
所以**两处都要看**：logger 放行了 DEBUG，还要保证控制台 appender 没有再把 DEBUG 滤掉。

**做法**：  
在 `logback-file.xml`（或你定义 console appender 的地方）里，把 console 的 `ThresholdFilter` 去掉，只靠各 logger 的 level 控制是否输出；若需要统一「最低输出级别」，用 root/logger 的 level 即可，不必在 appender 上再设一层阈值。

---

### 3. 换了 logback 配置文件名、甚至写了 `logging.config`，仍然不生效

**现象**：  
把配置改成唯一文件名（如 `logback-spring-search-service.xml`），并在 `application.properties` 里写了：  
`logging.config=classpath:logback-spring-search-service.xml`  
启动后加 `-Dlogback.debug=true` 也看不到 logback 的 “Using config file ...” 之类输出，感觉配置像被「盖掉」了。

**可能原因**：

- 项目里引入了**其他依赖**（例如 `gitcode-framework-log`），它们可能自带 `logback-spring.xml` 或 `logback.xml`，classpath 上谁先被加载就用谁，你的文件可能根本没被读到。
- 或者底层根本**不是 Logback**（例如被换成了 Log4j2），那所有 logback 相关配置都不会生效，`logging.config` 指向 logback 也没用。

**做法**：  
不依赖「到底用的是哪份配置文件」，直接在应用启动**之后**用 **Spring Boot 的 LoggingSystem API** 设一次该 logger 的级别，例如：

```java
LoggingSystem.get(Thread.currentThread().getContextClassLoader())
    .setLogLevel("com.xxx.SomeClass", LogLevel.WARN);
```

这样无论底层是 Logback 还是 Log4j2，只要走 Spring Boot 的 LoggingSystem，都会生效。  
可以写在一个 `ApplicationRunner` 里，启动完成后执行，并打一行日志确认「已设置 xxx 为 WARN（LoggingSystem: LogbackLoggingSystem）」方便排查。

---

### 4. 核心坑：代码里是 log.info()，你把 logger 设成 DEBUG 也「拦不住」这条 INFO

**现象**：  
已经用 LoggingSystem 或 logback 把 `com.xxx.ActionAccessAspect` 设成了 **DEBUG**，预期是「改成 debug 输出、少刷屏」，结果那条 `[ActionSdk] sendKafka uriMatchSuccess ...` 的 INFO 照样打。

**原因**：  
依赖里的代码写的是 **`log.info(...)`**，也就是说这条日志的**级别在代码里就定死了是 INFO**。  
你配置的是「这个 logger 的**输出阈值**」：设为 DEBUG 表示「只输出 DEBUG 及以上的日志」，INFO ≥ DEBUG，所以 INFO 一定会打；设为 WARN 表示「只输出 WARN 及以上」，INFO < WARN，于是这条 INFO 就不会再输出。

所以：  
- **不能**通过配置把「某一行 log.info()」变成「按 DEBUG 输出」或改成别的级别；  
- **能**做的只有：把该 logger 的阈值设为 **WARN（或 ERROR）**，让 INFO 不再满足「输出范围」，从而不刷屏。

---

## 三、核心概念：级别 vs 输出阈值（用比喻串起来）

可以把「日志」想成一批**要出门的快递**，每件快递上贴了一个**标签**：TRACE / DEBUG / INFO / WARN / ERROR。

- **代码里写 `log.info("xxx")`**：相当于给这件快递贴上了「INFO」标签，这件快递的「级别」就固定是 INFO 了，**配置不能改这个标签**。
- **配置里设 logger 的 level**：相当于在**门口**立了一块牌子：「只放行级别 ≥ 某级别的快递」。  
  - 牌子写「DEBUG」→ DEBUG、INFO、WARN、ERROR 都能出门；  
  - 牌子写「WARN」→ 只有 WARN、ERROR 能出门，INFO 和 DEBUG 会被拦下。

所以：  
- **谁决定「这件快递是 INFO 还是 DEBUG」？** → 代码里用的是 `log.info()` 还是 `log.debug()`。  
- **谁决定「哪些快递能出门」？** → 配置里该 logger 的 level（输出阈值）。  
你只能控制「输出范围」，不能把已经标成 INFO 的快递从配置里改成「按 DEBUG 出门」。

级别高低关系（数值上可以理解为：数字越大越「高」）：

```
TRACE < DEBUG < INFO < WARN < ERROR
```

一张简图概括：

```
                    ┌─────────────────────────────────────────┐
                    │  代码里：log.info("...") / log.debug("...")  │
                    │  → 这条日志的「级别」固定，配置改不了           │
                    └─────────────────────────────────────────┘
                                          │
                                          ▼
    ┌──────────────────────────────────────────────────────────────────┐
    │  配置里：logger 的 level（或 LoggingSystem.setLogLevel）             │
    │  → 相当于「输出阈值」：只输出 级别 ≥ 该阈值 的日志                    │
    │  例：设为 WARN → 只输出 WARN、ERROR；INFO/DEBUG 被过滤掉             │
    └──────────────────────────────────────────────────────────────────┘
```

## 四、小结（总）

- **配置不生效**时，可以按顺序排查：  
  1）Nacos/本地是否真的生效、是否被覆盖；  
  2）logback 里 console appender 是否还有 ThresholdFilter 把 DEBUG 拦掉；  
  3）是否有依赖自带 logback 配置、甚至底层根本不是 Logback；  
  必要时用 **LoggingSystem 在启动后代码里设一次级别**，绕过「谁才是真正生效的那份配置」的问题。

- **概念上**：  
  - 代码里 `log.info()` / `log.debug()` 决定的是**这条日志的级别**，不能通过配置改成别的级别。  
  - 配置决定的是**该 logger 的输出阈值**，即「只输出 ≥ 某级别的日志」，相当于控制**输出范围**。  
  想「不刷某条 INFO」→ 把对应 logger 的阈值提到 **WARN** 即可；想「多看 DEBUG」→ 把阈值设为 **DEBUG**，并保证 appender 没有再把 DEBUG 过滤掉。

把「级别是谁定的」和「阈值控制的是谁能出门」分开想，以后再配日志就不会懵了。
