## 起因：一个「或」

代码搜索原本只有一个关键词参数 `q`，DTO 上挂着 `@NotEmpty`，空了就报「搜索内容不能为空」。后来加了个 `symbol` 参数——只在 `type=code` 时透传到下游 zoekt 做纯符号搜索。需求跟着变了：不再要求 `q` 必填，而是 `q` 和 `symbol` 至少有一个非空。

`@NotEmpty` 到这儿就不够用了。它只认得「这个字段自己空不空」，管不了「两个字段之间」的条件。借这次改动，把 Bean Validation（JSR-380，`javax.validation` / `jakarta.validation`）在 Spring 里的几种写法从轻到重过一遍，每种配一段实际代码，最后给一张选型速查。

先抛结论：多数跨字段场景，用不上自定义注解那么重的家伙。

## 一、字段级内置注解（最常用）

直接挂在字段上，覆盖约九成场景：

```java
@NotNull              // 不为 null（可为空字符串、空集合）
@NotEmpty             // 不为 null 且 size > 0（String / 集合 / Map / 数组）
@NotBlank             // 不为 null 且 trim 后非空（仅 String）
@Size(min = 1, max = 50)  // 长度 / 元素个数范围
@Min(0) @Max(100)     // 数值范围
@Positive @Negative   // 正负
@Pattern(regexp = "...")  // 正则
@Email                // 邮箱
@Past @Future         // 时间
```

非空三兄弟最容易混，单独拎出来对一下——这张表后面还会再用到：

| 注解 | `null` | 空串 `""` | 纯空白 `"  "` | 适用类型 |
|------|------|----------|--------------|----------|
| `@NotNull`  | 拦 | 放过 | 放过 | 任意 |
| `@NotEmpty` | 拦 | 拦 | 放过 | String / 集合 / 数组 |
| `@NotBlank` | 拦 | 拦 | 拦 | 仅 String |

`@NotEmpty` 看的是 `length > 0`，所以纯空格串能蒙混过去；`@NotBlank` 会先 trim 再判空，纯空格也拦。字符串校验默认就该用 `@NotBlank`。

## 二、@AssertTrue / @AssertFalse（跨字段轻量校验）

挂在 boolean getter 上，把「条件」写进方法体，要求该方法返回 true（或 false）。适合临时的、一两处的跨字段规则：

```java
@Schema(hidden = true)
@AssertTrue(message = "搜索内容不能为空")
public boolean isQueryOrSymbolPresent() {
    return StringUtils.isNotBlank(q) || StringUtils.isNotBlank(symbol);
}
```

优点是零样板，逻辑直接写在方法里。代价有两个：一是错误绑定在这个「属性」上，而不是 `q` 或 `symbol` 某个具体字段；二是这个 `is...` 方法会被当成一个 bean 属性，可能漏进接口文档或 JSON 序列化里，所以加了 `@Schema(hidden = true)`，必要时再补 `@JsonIgnore`。

本次 `q`/`symbol` 的放宽就用了这种写法，修改一处同时校验两个字段，性价比最高。

## 三、自定义约束注解（跨字段的「正规军」）

当跨字段规则要复用，或要把错误精确绑定到某个字段时，自定义一个约束注解，通常挂在类级（`@Target(TYPE)`）：

```java
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = QueryOrSymbolValidator.class)
public @interface QueryOrSymbol {
    String message() default "搜索内容不能为空";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

public class QueryOrSymbolValidator
        implements ConstraintValidator<QueryOrSymbol, SearchQuery> {
    @Override
    public boolean isValid(SearchQuery query, ConstraintValidatorContext ctx) {
        return StringUtils.isNotBlank(query.getQ())
            || StringUtils.isNotBlank(query.getSymbol());
    }
}

@QueryOrSymbol   // 挂在类上
public class SearchQuery { ... }
```

比 `@AssertTrue` 重，三个文件加一套 `groups()` / `payload()` 样板，换来的是：注解名本身就是语义、可在多个 DTO 上复用，还能通过 `ConstraintValidatorContext` 把错误定位到指定字段。规则只此一家就别上它，要复用或要精确报错才值得。

## 四、分组校验 groups（同一 DTO，不同场景不同规则）

同一个类，新增时要求 `id` 为空、更新时要求 `id` 非空：

```java
public interface OnCreate {}
public interface OnUpdate {}

@Null(groups = OnCreate.class)
@NotNull(groups = OnUpdate.class)
private Long id;

// controller 用 @Validated 指定组
public X update(@Validated(OnUpdate.class) Foo foo) { ... }
```

要点：`@Valid` 不支持分组，只有 Spring 的 `@Validated` 支持。这是两者最大的区别。

## 五、级联 / 嵌套校验

校验嵌套对象或集合里的每个元素，在字段上加 `@Valid` 才会递归进去：

```java
@Valid private Address address;               // 进入 Address 内部继续校验
@Valid private List<@NotBlank String> tags;   // 校验集合每个元素
```

## 六、方法参数级校验（Service 层也能校验）

类上标 `@Validated`，约束直接写在方法参数上（依赖 `MethodValidationPostProcessor`，引入 validation starter 后自动配置）：

```java
@Validated
public class FooService {
    public void f(@NotBlank String name, @Min(1) int age) { ... }
}
```

让校验不只活在 controller 入参里。

## 七、编程式校验（不走注解，手动触发）

非 controller 场景，或需要条件性校验时，注入 `Validator` 手动调用：

```java
@Resource
private Validator validator;

Set<ConstraintViolation<SearchQuery>> violations = validator.validate(query);
if (!violations.isEmpty()) {
    // 自行处理
}
```

## 选型速查

| 需求 | 用法 |
|------|------|
| 单字段非空 / 范围 / 格式 | 字段级注解（`@NotBlank` 等） |
| 一两处跨字段条件 | `@AssertTrue` |
| 跨字段规则要复用 / 精确报错 | 自定义类级 `@Constraint` |
| 同 DTO 多场景不同规则 | 分组 + `@Validated` |
| 嵌套对象 / 集合 | `@Valid` 级联 |
| Service 层校验 | 类 `@Validated` + 参数约束 |
| 动态 / 条件校验 | 注入 `Validator` 编程式 |

## 附：@Valid vs @Validated

两个长得像，关键区别就这几条：

| | `@Valid`（JSR） | `@Validated`（Spring） |
|---|---|---|
| 来源 | `javax` / `jakarta.validation` | `org.springframework.validation.annotation` |
| 分组 `groups` | 不支持 | 支持 |
| 方法参数级校验 | 不支持 | 支持（类上标） |
| 级联嵌套 | 支持（标字段上） | 由 `@Valid` 负责 |

常一起用：controller 方法参数用 `@Validated` 触发并选组，DTO 内部的嵌套字段用 `@Valid` 级联。

## 本次实际改动

`SearchQuery`（所有搜索类型共用一个 DTO）原本是：

```java
@NotEmpty(message = "搜索内容不能为空")
private String q;
```

改成：

```java
private String q;
private String symbol;   // 仅 type=code 透传到下游 zoekt sym:

@Schema(hidden = true)
@AssertTrue(message = "搜索内容不能为空")
public boolean isQueryOrSymbolPresent() {
    return StringUtils.isNotBlank(q) || StringUtils.isNotBlank(symbol);
}
```

为什么不影响别的搜索类型：`symbol` 只有代码搜索会传，其它类型恒为空，条件 `q 非空 || symbol 非空` 自动退化成「q 必填」，和原来一致。只有代码搜索多出「只给 symbol 的纯符号搜索」这一条路。

有一处得诚实交代：原来的 `@NotEmpty` 放过纯空格串，新写法用的是 `StringUtils.isNotBlank`，纯空格会被拦——对 `q` 来说，比 `@NotEmpty` 卡得更死，相当于换成了 `@NotBlank`。但这恰恰是想要的：一串空格本就不该算有效搜索词。要是哪天真需要逐字符对齐老行为，把 `isNotBlank` 换回 `isNotEmpty` 即可。

一句话：跨字段校验有从轻到重一整排工具，先看规则是不是只此一处、要不要精确报错，再决定掏哪一件。多数时候，一个挂着 `@AssertTrue` 的 getter 就够了。
