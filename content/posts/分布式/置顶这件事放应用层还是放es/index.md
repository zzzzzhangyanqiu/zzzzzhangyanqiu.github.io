搜索结果本来应该按相关性排。谁最匹配，谁靠前。

但业务不会一直这么朴素。搜 `iphone`，运营希望某几个商品排在最前；搜一个开源项目名，平台希望官方项目先出来；某些活动位、赞助位、重点内容，也都可能要求“无论自然排序怎么打分，先把它顶上去”。

这件事通常叫搜索置顶。

它听起来像相关性优化，其实不是。置顶不会让某个结果变得更相关，它只是把一条业务规则压到相关性排序前面。问题也就跟着变了：这只手应该伸在应用层，还是伸到 Elasticsearch 查询里？

## 最常见的做法：应用层自己排

很多系统一开始都会把置顶放在应用层。

大概流程是这样：搜索服务先查 ES，拿到一页自然结果；再读一份置顶配置，比如“关键词 `iphone` 下置顶 `sku-1`、`sku-4`”；最后在服务里把这些文档挪到结果前面，再返回给前端。

这种做法很顺手。置顶本来就是业务规则，放在配置表里，走审核，加上下线时间，按频道、用户分群、实验桶继续拆，都很自然。甚至结果不完全来自 ES 也没关系，应用层拿到最终列表后再统一处理。

这就是应用层置顶最大的好处：自由。

但自由也要付账。最容易出问题的是分页。

第一页把某几个结果提到最前面，看起来不难。可第二页怎么办？置顶文档如果原本也在自然结果里，要不要从原位置删掉？第一页已经出现过的结果，第二页还能不能再出现？如果用户按价格、时间、下载量显式排序，置顶还要不要生效？这些问题只要有一个没想清楚，就会出现重复、漏数据，或者排序不稳定。

应用层置顶不是“把几个元素挪到数组头部”那么简单。它一旦接上分页、排序和去重，就变成了一段需要长期维护的搜索编排逻辑。

## ES 原生有一个 pinned query

Elasticsearch 其实提供了原生的置顶能力，叫 `pinned` query。

它的语义很直接：指定一批文档，把它们排在自然搜索结果前面。剩下的结果继续交给正常查询，也就是 `organic`。

一个最小例子是这样：

```json
GET /products/_search
{
  "query": {
    "pinned": {
      "ids": ["sku-1", "sku-4", "sku-100"],
      "organic": {
        "match": {
          "title": "iphone"
        }
      }
    }
  }
}
```

这里有两层结果。

`ids` 里的文档是置顶结果，按给定顺序排在最前面。`organic` 是自然搜索条件，命中的其他文档排在置顶结果后面，继续按正常相关性排序。

如果需要更精确地指定索引，也可以用 `docs` 写法：

```json
GET /products/_search
{
  "query": {
    "pinned": {
      "docs": [
        {
          "_index": "products",
          "_id": "sku-1"
        },
        {
          "_id": "sku-4"
        }
      ],
      "organic": {
        "match": {
          "title": "iphone"
        }
      }
    }
  }
}
```

`ids` 和 `docs` 二选一。`ids` 简单，适合只按 `_id` 置顶；`docs` 可以带 `_index`，在多索引搜索或者需要精确定位文档时更合适。

从使用者视角看，`pinned` query 把“置顶 + 自然排序”合成了一次 ES 查询。应用层不用先查自然结果，再手动挪位置。ES 会在查询阶段把指定文档放到前面。

它不是改写相关性算法，而是在相关性排序前面插入一段人工指定的结果。

## 最关键的限制：它只适合相关性排序

`pinned` query 有个很重要的边界：它设计上是配合相关性排序用的。

如果查询里写了显式 `sort`，比如按价格、创建时间、下载量排序，置顶效果会被覆盖。原因不难理解。`pinned` query 能把文档顶上去，靠的是给置顶文档一个特殊的高分，让它们在按 `_score` 排序时压过自然结果。可一旦显式按别的字段排序，最终顺序就不再看 `_score`，这层提升自然也就失效了。

很多业务里的“搜索”其实不只是相关性搜索。用户可能点了“最新发布”“价格从低到高”“下载量最多”。这时候还要不要置顶，本身就是业务决策。若答案是“无论按什么排序都要置顶”，那 `pinned` query 未必够用，应用层或者额外的排序设计仍然绕不开。

这点很容易被忽略。`pinned` query 适合的是一种比较窄、但很常见的场景：

> 在默认相关性排序下，把指定文档放到自然结果前面。

这个边界守住了，它就很好用。边界没守住，就容易误以为 ES 已经替业务系统解决了所有置顶问题。

## 置顶规则不应该全塞进查询里

还有一个问题更容易在落地时冒出来：`pinned` query 解决的是“怎么执行置顶”，不是“怎么管理置顶规则”。

比如这些问题，ES 查询本身并不会替你回答：

- 谁能配置置顶？
- 配置是否需要审核？
- 置顶什么时候生效，什么时候失效？
- 同一个关键词有多条规则时怎么合并？
- 不同频道、用户分群、实验桶下用哪套置顶？
- 置顶文档下线、删除、不可见时怎么处理？

这些都属于业务系统。

更合理的理解是：`pinned` query 可以成为执行层，但不应该被误当成规则中心。规则仍然可以放在自己的配置表、运营后台或者实验系统里。搜索时，应用层根据当前关键词、用户、频道和实验上下文算出一组置顶文档，再把这组文档塞进 `pinned` query。

这样一来，应用层没有完全消失，只是角色变了。

原来它负责“查完之后重新排结果”；现在它负责“算出本次查询要置顶谁”。真正的排序执行交给 ES。变化不大，但能少碰一类麻烦：分页、去重、自然结果合并这些事，尽量让它们回到 ES 的查询流程里。

## 那到底放哪一层？

可以按问题复杂度来分。

如果需求只是：某个搜索词下，把几个 ES 文档固定放在前面，默认按相关性排序，规则数量也不大，那 `pinned` query 很合适。它简单，语义清楚，也不需要应用层手写一套结果重排。

如果需求已经变成一套运营系统：有审核、有上下线、有分群、有 AB 实验、有商业策略，还要跨数据源合并结果，那规则中心还是应该放在应用层。ES 可以接收最终算出来的置顶文档，并负责执行，但不要把复杂规则硬塞进查询 DSL 里。

如果业务要求“无论用户按什么字段排序，置顶都必须在最前”，也要小心。因为这已经超过了 `pinned` query 最自然的使用范围。此时要么应用层兜底，要么重新设计排序字段和排序策略，不能只靠 `pinned` query 解决。

我的判断是：规则放应用层，置顶执行可以放 ES。

这不是折中话。搜索系统里很多能力都应该这么拆：业务规则留在业务系统，底层引擎负责它擅长的那部分执行。应用层不必亲自挪数组，ES 也不该背上运营后台的职责。

## 最后

`pinned` query 是一个很小的功能，但它切中了搜索系统里一个常见矛盾：自然排序追求相关性，业务排序追求可控性。

相关性排序是算法给出的答案，置顶是人插进来的答案。两者不冲突，但一定要分清楚谁在做什么。

把置顶完全放在应用层，灵活，但容易和分页、去重、排序稳定性缠在一起。把置顶交给 ES，干净，但它只适合按相关性排序时的指定文档置顶。实际落地时，最好别把两件事混成一件事：应用层管规则，ES 执行那次明确的置顶。

`pinned` query 不是相关性优化工具，它是 Elasticsearch 给搜索结果开的一道人工入口。入口可以开在 ES，钥匙最好还握在业务系统手里。
